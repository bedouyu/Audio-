# 自然语言音频中心重构

本次将 Audio智能助手从“先建学习项目，再生成课程”的工作台，调整为“描述想听什么，再持续收听”的个人音频中心。Java 后端、Electron/Vue 桌面端、既有资料和历史音频继续使用；没有扩展为内容版权平台或创作者市场。

## 1. 用户入口

首页提供一个自然语言输入框和可填入的示例句，不要求先选择新闻、小说、英语等模块，也不要求手动新建项目。

例如：

- “整理今天的时政，做成 10 分钟简报。”
- “讲一个适合睡前听的英文故事。”
- “把刚才那段改成英语，短一点。”
- “继续听。”

没有给出内容空间时，后端会按需要建立空间。已有空间用于保存资料、对话、草稿和音频，首页以历史记录呈现。语言、目标时长和表达方式都可以写在指令中，前端不再要求填写听众或课程时长表单。当前单次指令支持约 1—60 分钟的目标时长；目标时长是生成提示和原文选段预算，不是精确播放时长保证。

全局播放器在页面底部，返回首页、浏览资料或切换空间时继续保留；支持原生播放/暂停、前后切段及倍速。退出登录会暂停音频并清除当前播放器与媒体会话状态，账号各自保留恢复位置。

## 2. 内容准备路径

### 通用内容与原创故事

自然语言原文会传递给内容生成流程。系统只提取语言、时长、是否需要实时证据等提示，不会把每个请求都转成学习课程。

原创故事可以按要求生成、续写或改写。接续和修改可使用指定上一队列的有界文字稿上下文；它没有完整长篇小说的人物库、剧情状态或长期一致性保证。只有明确要求按学习计划或下一个知识点生成时，才沿用既有知识点规划。

生成模型未配置、返回空正文或正文语言不符合要求时，队列显示真实错误，不会用“定义—组成—流程”等固定课程模板代替请求。原有基础知识问答的摘录式兼容模式与通用音频正文生成是不同能力，不能据前者推断后者在没有模型时仍能创作。

### 时政与新闻

实时新闻请求使用 Bing 新闻 RSS 搜索摘要，要求条目具有可解析的发布日期、符合请求时间范围，且不能以未来发布时间冒充当前新闻。同一链接会去重；来源元数据保存 `published_at`、`fetched_at`、`source_host` 和证据类型。日期解释以北京时间为准。

新闻 RSS 使用 `www.bing.com/news/search`，按日期排序。新闻检索适配器移除制作音频的前后缀和不受支持的 `after:/before:` 搜索语法，提取主题；完整用户指令仍交给生成模型，时间范围仍按条目的实际发布日期校验。HTML 页面会明确报错，不作为 RSS 解析或无结果处理。普通网页检索保持原查询。

没有明确时间时，当前默认检索最近约一周；指令可以写今天、昨天或具体日期范围。联网未启用、读取失败，或没有足够的带日期条目时，会明确失败，不会用本地旧资料冒充最新消息。

**搜索摘要没有等同于报道全文，也没有完成独立事实核查。** 当前未自动抓取报道正文，不保证全面覆盖、不代表权威新闻编辑判断，也没有自动 RSS 订阅或每日定时播报。重新改写旧音频可能沿用其原来源；`reverified=false` 的引用会提示“沿用原音频来源，未重新检索”，不能理解为本次又核验了新闻时效。

### 完整原文朗读

在首页点击“添加资料”，系统通过原有项目接口自动取得“我的资料”空间并打开导入页，不调用模型或生成音频。已有空间也可以直接打开“资料”上传小说、文章等完整原文，再回到“收听与制作”说明资料完整标题和章节。多份原文无法唯一确定时会要求明确选择；API 调用也可使用 `source_record_id` 精确指定资料。

首次使用也可以先导入资料，再开始收听，无需先建立生成任务。但仅输入“朗读某书”不会获得系统里不存在的原文。资料页会标出是否支持原文朗读；旧资料若没有完整原文索引，需要重新上传原文件。

原文朗读从保存的完整文本中选取连续范围，记录文档版本、起止位置及总长度；支持识别常见中文章节和 `Chapter N` 标题。每次按目标时长选择有限范围，遇到下一章节边界会结束，不保证一次读完整章。原文不会交给模型重新创作，也不会从检索片段拼凑或编造原书。朗读缺少资料、章节不存在、版本变化或没有下一章时会明确说明。

“下一章”选择后续章节；“接着读原文”可以继续当前章节尚未覆盖的范围。原文范围表示本次准备了哪些文字，实际听到哪里另由播放进度记录。已导入完整原文可以不调用生成模型直接朗读，但仍需要可用的本机语音。

### 英语与中英双语

指令可以明确要求英文或中英双语。生成结果会做基本语言检查；语音使用本机 Windows System.Speech 真实安装并启用的音色。英文内容需要英文语音；双语内容需要中文和英文语音，并按文本语言切换。指定音色不支持请求语言，或本机没有对应音色时，会明确失败，不会默默换成中文音色。

音色列表读取失败时，界面说明生成时会再次检查本机语音能力。当前没有接入商业语音服务，也没有逐句跟读评分、发音评测或完整语言教学体系。

## 3. 自然语言 API

以下接口继续使用既有账号鉴权。音频、空间和资料均先验证当前用户的所有权。

### `POST /api/v1/audio/requests`

最小请求：

```json
{
  "instruction": "讲一个 5 分钟的英文睡前故事",
  "request_id": "4aa124a5-e1f3-4c7c-8cd6-b29249bd57e9"
}
```

| 字段 | 要求与用途 |
| --- | --- |
| `instruction` | 必填，完整收听指令。当前桌面输入上限 4000 字，后端校验上限 5000 字 |
| `request_id` | 必填，标准 UUID；同一意图重试必须沿用原值 |
| `project_id` | 可选，已有内容空间编号；缺省时按需要自动建立或由上下文确定 |
| `previous_queue_id` | 可选，实际要接续或修改的队列 UUID，必须属于当前用户及对应空间 |
| `source_record_id` | 可选，精确指定已上传资料记录；缺省时根据资料标题及上下文选择 |
| `voice` | 可选，真实已安装且启用的音色名称；不传时按内容语言检测本机能力 |

前端遇到“刚才、这段、继续、接着、换成、改成、缩短、下一章、新进展、新消息”等上下文表达时，发送当前全局播放器的 `previous_queue_id` 与该播放器的 `project_id`。即使用户在首页，或正在查看其他空间，也不会把无关空间的最近一条队列当作这段音频。全新指令可以不附带上一队列。

响应包含 `project`、`action`、`request_id` 与队列快照，包括 `queue_id`、`status`、`lessons`、`segments`、`total_segments`、`citations`、`context` 等。

- `action=GENERATE`：新请求已建立生成任务，不代表正文或音频已经完成。
- `action=RESUME`：使用已有队列。它可能是继续收听，也可能是同一 `request_id` 的回执重放；客户端恢复该队列进度，不清零重做。
- 非终态通常返回 HTTP `202`；已完成、失败或需要人工核查等终态返回 `200` 及实际状态。客户端应以队列状态和错误内容判断结果，不能仅看 HTTP 请求成功。

`audio_instruction_receipts` 将用户、请求 UUID、参数指纹、空间与目标队列绑定。相同 `request_id` 和相同参数重放返回同一队列；改动指令、来源、音色、空间或 `previous_queue_id` 后仍复用该编号会冲突。前端在传输失败时保留原请求键，明确收到队列后才为新任务建立新键。

准备失败或结果不确定不代表可以自动再次调用模型或语音。失败任务不会因重复提交同一个请求键自动重做；确需新任务时应明确发出新请求。接续已有队列的回执也会持久化，避免原队列听完后重放旧请求意外生成后续内容。

### 历史、音色与播放进度

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/audio/history` | 返回当前用户的 `{queues: [...]}`；可加 `project_id` 限定空间 |
| `GET /api/v1/audio/voices` | 返回真实本机音色 `{voices: [...], default_voice: ""}`，包括名称、语言及启用状态；桌面过滤 `enabled=false` |
| `GET /api/v1/audio/queues/{queueId}/progress` | 返回已保存播放位置；无记录时默认第 0 段、0 秒、1 倍速、未听完 |
| `PUT /api/v1/audio/queues/{queueId}/progress` | 保存 `segment_index`、`position_seconds`、`playback_rate`、`completed` |

播放片段下标 `segment_index` 从 0 开始。进度写入只接受已经 `READY` 的片段；只有队列完成且处于最后一段时才能标记 `completed=true`。桌面在实际末段播放结束时标记听完，生成完成不会自动变为已听完。

播放中约每 5 秒同步一次服务端进度，暂停、切段和退出时主动保存；更新按顺序发送，降低旧位置后到覆盖新位置的风险。本机存储保留每个用户最近播放器的恢复副本，含位置、倍速、`completed` 与实际进度更新时间 `savedAt`。恢复时比较本机时间与服务端 `updated_at`：较新的本机记录保留并随后同步，服务端较新则采用服务端记录。任务状态轮询不会给未变化的播放位置重新标新时间，也不会重复上传未变化的位置。服务端不可用时可从本机副本恢复；退出后的迟到请求和进度响应不会重建其他账号的播放器。

历史队列可以直接恢复播放，不调用音频生成。`lessons` 仅包含可播放的片段，客户端按每项的 `segment_number` 对齐真实顺序，不能把过滤后的数组下标当成原片段编号。

## 4. 队列与原有能力

自然语言请求先在短数据库事务内保存回执和队列，随后由有界后台执行器准备内容与合成。初始可能是 `PREPARING`，其后状态由真实执行结果更新；MySQL 始终是执行事实来源，Redis 仅缓存快照。

开放式生成（没有选定原文、也没有上一段可接续）的内容准备现在走多智能体运行时：主控委派研究/写稿/复核，取出通过复核的 `SCRIPT_DRAFT` 再进入分段与合成；`GET /api/health` 的 `instruction_audio_runtime` 会显示 `multi-agent` 或 `single-shot`。被队列消费的草稿状态置为 `CONSUMED`，任务随之收敛为成功，不再停留在"待你确认"；该产物也不能再走人工确认合成。这类请求不额外写聊天轮次或项目记录，避免同一次请求出现两条内容记录。忠实改写、接续上一段和原文朗读仍走单次生成——它们做的是「按给定文本变换」，不该把长原文塞进多轮上下文。多智能体没有产出可用草稿时，队列以失败结束并给出原因，不会退回模板或占位正文。

原有 `GET /api/v1/continuous-audio/{queueId}` 查询，以及 `/refill`、片段 `/recover`、`/reset` 继续使用。未知合成结果需核验已有 WAV，或填写理由人工重置，再明确继续生成，不会悄悄重试 TTS。返回 `NEEDS_REVIEW` 需要先处理不确定结果。

### 改讲稿

`POST /api/v1/continuous-audio/{queueId}/segments/{number}/revise`，请求体二选一：

- `{"instruction": "太书面了，改口语一点，保留原来的例子"}` —— 模型按意见改写**这一段**
- `{"text": "……"}` —— 直接用手工文本替换这一段（不调模型）

两种方式都只改这一段讲稿并**只重新合成这一段**，其余片段不动。要点：

- 模型只拿到「这一段原文 + 修改要求」，提示词要求保留未提及的部分、保持语言与口语风格，避免像整篇生成那样重写全文
- 语言必须与原文一致，否则 400；模型改写还限制长度变化在 0.5—2.0 倍之间，防止"改一句变成另一篇"。手工编辑不受该限制
- 旧讲稿、旧哈希、旧音频编号和修改说明都写进片段审计；旧音频进 `retired/`，按保留时长清理
- 该段回到 PENDING 并重新合成，`script` 与 `script_hash` 现在是可更新字段
- `ContinuousAudioStore.segmentScript` 不能用只读事务：它读的那一行会加写锁，只读事务里加锁查询会被数据库拒绝（MySQL 1792）

### 换音色重制

`POST /api/v1/continuous-audio/{queueId}/revoice`，请求体 `{"voice": "音色名"}`。

已经做好的音频可以只换声音、不重写内容：服务端把每条已完成片段的音频编号换新，用新音色重新合成，讲稿、分段和标题都不变。因为不经过模型，这项操作**没有 token 成本**，代价与音频时长同量级的合成时间。

- 每段内容的语言都必须被新音色支持，否则在开始合成前返回 400，不会产生半成品
- 队列正在生成、或有片段等待核验时拒绝（409），避免与运行中的合成抢同一个片段
- 换音色属于同一条目的重制：旧的 lesson 记录会被替换，历史里不会出现重复条目
- 被替换的旧音频不立刻删除，先移到 `data/generated-audio/retired/<到期时间戳>_<audioId>.wav`，默认保留 8 小时（`audiorag.audio.retention-hours`）后由定时任务清理；到期时间写在文件名里，重启后依然生效
- 队列快照新增 `voice` 字段（实际使用的音色），历史与界面据此显示

旧项目、资料上传/下载/删除、知识库检索、聊天会话、Agent 草稿和产物审核、调用轨迹、单节与连续音频接口保留。旧学习计划页面明确说明“已完成”仅指音频生成记录，不代表听完或掌握。历史 RAG/Memory 实验脚本和文档没有因本次重构被重新解释为新的生产评估结果。

## 5. 数据与启动

本次新增数据库表仅为：

- `audio_instruction_receipts`：自然语言请求的幂等回执。
- `audio_playback_progress`：按所属用户、空间和队列保存实际收听进度。

既有表名、资料与音频保留，没有删除或重命名旧表。原有队列命令 JSON 承载指令、来源范围和上一队列上下文，不需要将旧队列重建成新内容。

**用户自行重启更新后的后端前，应备份现有 MySQL。** 继续使用现有 JPA `ddl-auto=update` 设置，下一次启动时增量更新结构；若用户自行覆盖为其他 DDL 策略，应按其策略安排迁移。本次未连接生产服务执行数据库改动，也未替用户停止或重启现有服务。

启动方式不变：先启动已有 MySQL、MinIO、Qdrant、Redis，再运行 `start-backend-local.cmd` 与 `start-frontend-local.cmd`。私有服务配置仍保留在 `backend/config/application-private.yml`，模型密钥仍读取 `DEEPSEEK_API_KEY` 或 `AUDIORAG_LLM_API_KEY`。本机语音脚本位于 `tools/synthesize.ps1`。
