## 三、八个最容易被追问穿的点

### A. “多 Agent”是不是并行？

真实回答：主控用 delegate_agent 委派四类专业 Agent，子 Agent 新建独立消息上下文，共享 budget 和 evidence，并使用同一个配置的模型网关。四类 Agent 不是四套模型部署。调用是同步串行，不是分布式任务调度。

追问“多个 Agent 能否互相无限委派”：子 Agent 没有 delegate，禁止委派主控，根预算 24 次模型/32 次工具/8 次委派/10 分钟。单 Agent 步数另限；同 Agent + 工具 + 规范化参数最多两次。输出校验额外修复机会最多一次。

追问“不断换查询词呢”：重复检测可能不触发，当前靠总预算；没有语义无进展判定。10 分钟是协作式预算检查，不是任意阻塞代码的硬终止。

### B. “分层 Memory”是不是分层摘要/无限记忆？

真实回答：原始会话、带来源的原文摘记检查点、查询时组装的上下文是三层。支持 recent_window/query_recall/extractive_notes/hybrid，不用派生摘记覆盖完整历史。

每次默认最多扫描 400 消息，摘记最多 32 条、每条最多 300 UTF-16 字符；原文摘记按目标/约束/更正等字面启发选取。带 source_id、原文范围、turn_id、来源哈希。检查点回载会验证原文位置、文本和 role/turn_id/content 的哈希。

“继续”可用当前扫描历史内最近的非继续用户问题扩展 BM25 查询；不是搜索无限历史。窗口外旧内容只有保留下来的有效摘记或已知 source ID 能按需核对。新更正优先并不等于自动语义冲突消解。

不能回答“分层 LLM 摘要”“用户画像持续学习”“所有历史偏好永不遗忘”。

### C. “检查点/状态恢复”能从第 N 步续跑吗？

真实回答：不能。完整聊天和任务/产物持久化后可以回载目标、状态和产物参考；重启将运行中任务标中断，不自动重放工具。下一次“继续”是基于已有记录开展新运行。

Memory 检查点保存的是原文摘记，不是 Agent 的程序计数器或模型协议栈。内存 transcript、预算、证据账本、阅读/复核账本和未结束工具调用没有完整执行级快照。

音频中断另有人工核验原 WAV/明确重置尝试的流程，不等于自动续跑所有工具。启动时全量 RUNNING 标中断也是单实例假设，多实例不能直接复用这一做法。

### D. “上下文预算”是否是跨供应商精确 token？

真实回答：目前不是。Memory 默认预算是 6000 个序列化 JSON 字符，当前 Agent 消息总预算 48000 字符；旧工具观察可压到 1000 字符，执行器单次观察上限 8000 字符。元数据、转义等计入各自 JSON 长度。

这些长度限制不能替代生成模型 tokenizer。BGE token 计数主要用于 embedding 切片与 RAG 组装。AgentTranscript 目前计 messages，工具 schema 是另传到模型网关的，未被统一计入 48000；也没有完整输入/输出 token 窗口预留。max_tokens=8192 是生成输出上限，不是输入预算。

超过当前字符限制时优先压缩旧工具观察，保留 assistant/tool 协议配对及供应商必须回灌的 reasoning_content；仍不够就停止，不截断必要协议继续。

后续可做模型特定 TokenCounter、全请求计量、输出预留及 usage 校准，但这些不能写成当前能力。

### E. “请求幂等”是否所有重试都只执行一次？

真实回答：聊天通过 user/project/request_id 唯一约束和规范化请求 SHA-256 识别重发，重放先于创建 session 和模型调用。相同编号不同请求拒绝；完成/待确认结果复用；运行中、失败、中断等不自动重跑。新 UUID 是新请求，不做语义相同去重。

草稿确认另用当前内容哈希、审核报告或显式覆盖理由、run→artifact 锁顺序及终态复用。READY/APPLIED 可复用，GENERATING/NEEDS_REVIEW 不自行再次执行。

不能说“全站幂等”：旧 lessons/continuous 入口不由新聊天 request_id 协议覆盖。跨实例同会话不同 request_id 没有分布式锁；进程内会话冲突目前还可能走普通 API 500，而不是统一 409。

### F. “Redis/MySQL 一致性”如何回答？

不能直接套“缓存双删”：Redis 在本项目存连续课程队列快照，MySQL 存课程记录，两者不是简单查询缓存关系。

当前流程：TTS → MySQL recordLesson → 内存 lessons.add → Redis save。若 MySQL 已记而 Redis 尚未保存就退出，恢复旧快照时按 lessons.size 计算下一段，可能再次合成同一段。Redis 过期/丢失也没有完整 MySQL 队列重建协议。

单进程 synchronized、Redis TTL 和保存快照不能保证跨存储原子性。没有事务 Outbox、segment 幂等唯一键、版本 CAS 或后台对账。

后续设计可以是以 MySQL 的任务/片段状态为事实来源，按 queue_id + segment_no + script_hash 约束片段幂等，Outbox 或对账同步 Redis；但本次只是列出方案，没有实现。

### G. “BGE-M3/RRF/RSE/rerank”如何区分？

当前默认和最近离线评测是中文 bge-small-zh-v1.5 ONNX。未找到专门 BGE-M3/XLM-R 或 cross-encoder reranker 实现。自写 BERT tokenizer/固定 ONNX 输入输出不能因为可改模型路径就声称任意模型兼容。

BM25 是词法召回，dense 是稠密向量召回；RRF 取各路排名，用 `sum(1/(60 + rank + 1))` 融合，避免直接混加不同量纲分数；不是 reranker 或相关概率。

邻居扩展是固定 ±1。RSE 是 rank-proxy 变体：命中效用近似 `exp(-rank/10)-0.2`，未命中为负值，贪心选择连续高效用区间、最多 6 片、防重叠并受 token 预算约束。不是全文语义分节或完整原方法复现。

原文、版本、顺序、坐标保存在 MySQL；同一个 Qdrant collection 按项目/版本筛选。各召回/组装方法使用共享规范片段，不为每种策略创建生产数据库。BM25 当前按请求读片段并构建，不是大规模持久倒排引擎。

### H. “模型自主选择”是否有收益证明？

功能层：工具参数允许模型选择 dense/bm25/hybrid 与 top_k/neighbors/rse_rank_proxy，后端记录请求、实际策略、选择依据、警告，并在前端展示。

效果层：已有本地诊断集是 6 份人工中文文档、18 个问题，1458 是组合条件记录，不是独立问题数；片段最多 21，候选深度 50，dense 实际包含全部片段。离线 exact cosine 不等于生产 ANN 搜索。dev/test 是按题标记，不是文档级留出。

观察到特定条件下 RSE 比 Top-K 覆盖高，也观察到 BM25 小预算下 RSE 更差。指标是证据覆盖，不是回答正确率。实验没有让真实模型选策略，不能声称最优路由、准确率提升或企业规模泛化。

## 四、运行观测的准确口径

原生事件包含 run_id、agent_id、iteration、共享 sequence，MySQL 保存事件后 SSE 发送，桌面可查看任务和产物轨迹。可以分析失败、重复工具、限制触发和降级。

但 tool_start/end 没有保存 tool_call_id，没有标准 parent_span、子调用实例编号、重放游标、去重和乱序重排。模型协议内部 call_id 配对不等于持久 Trace 已完整保存这些信息。基础检索模式还存在按 session 返回全量轨迹、缺少 run_id 的不同口径。

所以简历可以写“执行过程记录/工具调用轨迹持久化”，不要新增“分布式 Trace”“非侵入 Hook”“任意异步乱序关联”“企业可视化观测平台”。

工具 RuntimeException 会回灌 ERROR，NO_RESULTS/TRUNCATED 不计成功。但统一执行器同步调用工具；模型、Web、HTTP/TTS 只是各自有超时，数据库或不响应中断的工具仍可能阻塞。Web 搜索还存在异常返回空列表的边界，没有全工具一致的错误分类。

## 五、简历关键词对应的准备要求

| 简历关键词 | 至少应独立讲清 |
|---|---|
| 多 Agent / ReAct / Function Calling | 主控和子 Agent 的调用链、调用协议与观察反馈、同步/并行区别、结束条件、框架取舍。 |
| 独立上下文 / 工具权限 | 子消息只拿 task/显式产物；证据账本共享；后端白名单/schema/归属，而不是单靠提示词。 |
| 共享预算 | 24/32/8/10分钟及各 Agent 步数；参数重复检测；不是费用预算或阻塞代码硬超时。 |
| 分层 Memory / 检查点 | 三层分别是什么、messages/turn_id/摘记范围/hash、400/32/6000限制；检查点不等于运行快照。 |
| BM25历史召回 / 按需重读 | 历史分段、BM25当前窗口检索、source限定的原文读取；不是无限记忆或持久倒排服务。 |
| 状态恢复 | 原目标/状态/产物回载、中断标记和人工核查；不是原运行从下一步无损继续。 |
| RRF / RSE式 | 排名融合公式、两路来源、连续段效用与邻居差异；至少一个反例和实验局限。 |
| 自适应 / 自主策略 | 实际可选参数及默认策略、记录实际结果；支持选择但未证实最优。 |
| 请求幂等 / 确认审计 | 作用域、key/hash、唯一约束、状态/锁、重试语义、审核版本；不能泛化成全入口 exactly-once。 |
| 显式降级 | 哪些临时向量故障可降级、新版/旧版索引差异；认证、维度等不静默降级。 |

每个词准备四件东西：一处代码、一个失败情形、一份验证证据、一个明确边界。不能靠换词掩盖未掌握的机制，也不必把截图里所有功能都加到简历。

## 六、建议的简历三条

- 设计主控与专业 Agent 的同步协作机制，基于原生 Function Calling 实现 ReAct 式工具调用与观察反馈；通过独立上下文、工具白名单与共享调用预算约束执行，结合产物校验、审核内容一致性检查、聊天请求幂等与确认审计，形成规划、生成、复核及人工确认执行闭环。
- 设计会话 Memory 与上下文管理机制，基于持久化历史和可追溯原文摘记检查点，支持滑动窗口、BM25 历史召回及混合策略；结合按需重读、历史任务与产物回载、结构化工具观察压缩，控制上下文长度并保留来源追溯能力。
- 设计项目隔离的自适应 RAG 链路，基于文档版本、片段顺序与原文坐标构建共享索引；支持模型选择召回与证据组合策略，提供 Top-K、邻居扩展及 RSE 式连续证据组合，记录实际检索策略与降级原因。

这三条不新增未实现能力，也不承诺效果提升。若保留原来“分层 Memory”和“任务状态恢复”，必须按上文解释，而不能引出分层摘要和执行级 checkpoint/resume 的错误承诺。

## 七、下一步改进优先级（本次未实施）

1. **覆盖旧连续课程写入窗口**：片段事实状态、唯一键、结果对账，解决 MySQL/Redis 保存之间可能重复合成的问题。
2. **统一工具 deadline 与错误语义**：将 deadline 穿透到实际 IO/查询/进程，对结果未知的写入采用待核查；不能只包 Future 就声称任意写入可安全取消。
3. **真实模型与长会话评测**：同模型同预算对照固定/自主策略，扩大语料、困难负例、零召回和文档级留出；先证明收益再写指标。
4. **精确上下文计量**：涵盖 system/history/tool schema/输出预留的模型特定 token 预算，保留不可拆的工具协议。
5. **工具调用级可观测性**：call_id/子调用实例/parent关联与事件契约，为未来并行、乱序和重放做准备。
